# Governance

The project currently uses a **maintainer-led research software model**.

## Decision classes

- **Factual/research truth:** never decided by vote; evidence, proof, execution, and scoped source support govern claim status.
- **Project direction and release scope:** maintained by the repository maintainer, informed by issues, experiments, and contributor evidence.
- **Code/research changes:** reviewed through pull requests with explicit verification and reproducibility information.
- **Security fixes:** may be handled privately before public disclosure.

## Change policy

Core behavioral mechanisms require stronger evidence than documentation or presentation changes. Experimental mechanisms may exist behind clear labels; they should not be described as validated until the relevant evidence exists.

## Compatibility

Professional display names may evolve, but stable technical IDs and command aliases are retained when practical. Breaking changes require a changelog entry and migration note.

## Releases

Stable releases should have a version, changelog entry, citation metadata, passing required checks, and a frozen evidence boundary. Evidence-bearing releases should be archived with a DOI when appropriate.
